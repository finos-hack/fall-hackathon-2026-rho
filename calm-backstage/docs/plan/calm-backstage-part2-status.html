Deviations from the plan

  • D1The plan put the cluster at step 3. It was started first, by the lead, because steps 4 to 6 depend on it and it was the least certain part. Measured: profile calm-backstage (Kubernetes 1.37.0, Calico, 3 GB) is up; ~/.kube/config has the same checksum as before and the active context is still minikube. Step 3 now only adds the yarn scripts. applied
  • D2Risks probed before building. Calico enforces: a default-deny policy blocked a test pod, DNS included, so the bundle's policies must allow DNS. The Hub accepted a deployment decorator (201) in a scratch namespace, so the step 7 fallback is unlikely to be needed. documented
  • D8The first video showed Backstage only. Jim asked for CALM Hub in it. The Hub UI showed "No deployment history" for our decorator: it looks decorators up by the architecture's numeric path with hyphens in the version, not the name-based path. The decorator now names both, and the Hub's Deployments tab shows the deployment. applied
  • D7Found in the from-scratch run: with no cluster, a run with the deploy box ticked (the default) failed at the image build after it had already stored the architecture in the Hub and published files. A new first step, calm:cluster:check, now stops such a run before it writes anything; measured: the run fails at check-cluster, with no folder and no Hub document. applied
  • D6The plan expected the Hub to accept a generated architecture as it is. It refused it: a title is required (calm generate sets none), the name must start with a letter, and the first version must be 1.0.0. The run now sets the title to the service name, and the name field requires a leading letter. A marker in the architecture's metadata stops the catalog showing a stored service twice. The findings are in FINDINGS.md. applied
  • D5Found in step 4: the scaffolder renders step conditions with nunjitsu, and a render error leaves a truthy string, so a wrong condition would run the step instead of skipping it. The build and deploy conditions were evaluated with that renderer before use. Also added: the deploy action only reuses a namespace that carries the service's own label, so a service name cannot reach another calm- namespace. applied
  • D4A subagent's check printed part of the git-ignored app-config.local.yaml, including the cluster's read-only service account token, into its own tool output. The token only reads the local calm-backstage cluster (no secrets) and was not copied anywhere; yarn k8s:down then k8s:up replaces it. Later subagents are told not to read that file. documented
  • D3The plan had one NetworkPolicy per connection. A policy selects one set of pods, so each in-cluster connection gets two (egress from the source, ingress to the destination): 11 policies for a service with three dependencies. The gateway forwards plain HTTP although the architecture says HTTPS; no certificates are rendered. applied
